Architectural Guide: Zero-Overhead Secret Management & Google Authentication

A practical look at keyless CI/CD and Google sign-in—and the security boundaries that matter when designing a low-overhead Google Cloud and Firebase architecture.

1. Introduction: Low-Overhead Infrastructure

Teams can often avoid adding a separate identity or secret-management vendor by using services they already operate. That does not make a design free, automatically secure, or exempt from usage charges: review current Google Cloud and Workspace pricing, quotas, licensing, and operational requirements before adoption.

The goals are to remove long-lived credentials from CI/CD, give each workload only the permissions it needs, and use a managed sign-in flow for client applications. Workload Identity Federation (WIF) can exchange a GitHub Actions OIDC identity for short-lived Google Cloud credentials; Firebase Authentication can provide Google sign-in for an application.

Security boundary: A Google Sheet is not a secrets vault. Google encrypts Workspace data at rest and in transit, but sheet protections and hidden cells do not prevent permitted viewers from reading the contents. Keep credentials in a dedicated secret store such as Google Cloud Secret Manager.

2. Architecture Overview: Configuration and Secrets

A restricted Google Sheet and Apps Script can be useful for low-sensitivity operational configuration. For actual credentials, prefer Secret Manager with narrowly scoped IAM. Both can be retrieved at runtime over TLS, but only the latter is purpose-built for secret versioning and access control.

GitHub Actions ── OIDC token ──> Workload Identity Federation
                                      │
                                      └── short-lived identity
                                             │ least-privilege IAM
                                             v
                                    Secret Manager (runtime)

Firebase client ── Google sign-in ──> Firebase Authentication

Apps Script + restricted Sheet ──> non-sensitive configuration only

Infrastructure workflow

  • Storage: Store sensitive values in Secret Manager. Use Sheets only for data that is safe for every authorized spreadsheet viewer.
  • Access control: Grant named principals the minimum permissions needed. Sheet protection controls editing, not confidentiality.
  • API interface: Use Google Cloud IAM and WIF for workload identity. An Apps Script web app configured to execute as its owner can expose the owner's access to callers; deployment access settings must be treated as a security boundary.
  • Consumption: Retrieve only the secrets required by a job, keep them in process memory where possible, and never print, persist, or pass them in URLs.

3. Apps Script: Use a Restricted Configuration Endpoint Safely

The original pattern of placing an API_SECRET_KEY in a query parameter is not safe for secret distribution. URLs can be captured in browser history, proxy and server logs, analytics, or diagnostic output. A bearer token in a URL also is not OAuth authentication simply because it is called a token.

If an Apps Script endpoint is needed for non-sensitive configuration, restrict the web app to the intended Google Workspace audience, execute it with the least privileged account possible, and do not return secret values. Keep spreadsheet access private; do not rely on cell or sheet protection to hide values from viewers. For credentials, have an authenticated workload access Secret Manager directly instead.

Deployment check: Avoid “Anyone” access for an endpoint that runs with the owner's privileges. Do not deploy a public doGet that returns a spreadsheet's contents based only on a caller-supplied shared token.

4. Passwordless CI/CD: Workload Identity Federation

Service-account JSON keys stored in GitHub Secrets are long-lived credentials that can be copied or leaked. WIF lets Google Cloud validate the OIDC identity issued to a GitHub Actions job and issue short-lived credentials instead.

Configuration protocol

  1. Create a workload identity pool and OIDC provider in the target Google Cloud project. Use the GitHub Actions issuer, https://token.actions.githubusercontent.com, and map only the attributes needed for authorization.
  2. Bind the intended GitHub repository identity to a dedicated deployment service account with roles/iam.workloadIdentityUser. Restrict the provider condition to the exact repository and, where practical, the intended branch or environment.
  3. Grant the service account only the required deployment and secret-access roles. Avoid project-wide roles and wildcard repository bindings.
  4. In GitHub Actions, request an OIDC token and authenticate before accessing Google Cloud.

GitHub Actions authentication workflow

After configuring the repository variables shown below with the real provider resource and service-account email, this minimal workflow uses the official authentication action to exchange the job's OIDC token. Keep id-token: write limited to jobs that need it.

permissions:
  contents: read

on:
  workflow_dispatch:

jobs:
  authenticate:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ vars.GCP_WIF_PROVIDER }}
          service_account: ${{ vars.GCP_DEPLOYER_SERVICE_ACCOUNT }}

Configure GCP_WIF_PROVIDER and GCP_DEPLOYER_SERVICE_ACCOUNT as repository or environment variables; they identify resources, not secrets. Pin third-party Actions to reviewed commit SHAs in production workflows, and review Google's current action guidance before deployment.

For a secret needed by a job, grant narrowly scoped Secret Manager access and retrieve it at runtime. Avoid shell tracing and output commands that persist secret values beyond the step; mask values if they must be passed between steps, and ensure deployment tools do not print them.

5. User Authentication: Firebase Google Sign-In

Firebase Authentication can handle Google sign-in for client-facing web applications, avoiding custom password handling in the application backend.

Firebase setup

  1. Create or select a Firebase project linked to the appropriate Google Cloud project.
  2. In Firebase Authentication, enable the Google provider and configure the support email.
  3. In the Authentication settings, authorize only the domains used by the application. Remove development domains from production when they are no longer needed.
  4. Configure Firebase Security Rules and backend authorization independently; a successful sign-in does not by itself authorize access to application data.

JavaScript client example

Initialize the Firebase Web SDK with the project's client configuration. The Firebase web API key is public configuration, not an authorization secret; secure data with Authentication, Security Rules, and any required API restrictions.

import { initializeApp } from "firebase/app";
import {
  getAuth,
  GoogleAuthProvider,
  signInWithPopup
} from "firebase/auth";

const app = initializeApp(firebaseConfig);
const auth = getAuth(app);
const provider = new GoogleAuthProvider();
provider.setCustomParameters({ prompt: "select_account" });

export async function handleGoogleLogin() {
  const result = await signInWithPopup(auth, provider);
  return { user: result.user };
}

Handle popup errors in the application UI and follow Firebase's current guidance for redirect-based sign-in where popup flows are unsupported. Do not treat an ID token or access token as a substitute for server-side authorization checks.

6. Deployment Checklist and Best Practices

Control areaRecommended actionPriority
Secret managementStore credentials in Secret Manager and limit access to explicitly named workloads. Do not store secrets in a broadly viewable Sheet.Critical
Access auditingEnable and review relevant Cloud Audit Logs, including secret access and IAM changes.High
Workload Identity FederationRestrict provider conditions to the exact repository and trusted branch or deployment environment; avoid wildcard trust.Critical
Credential lifetimeUse short-lived federated credentials and the narrowest practical token lifetime.High
Firebase AuthenticationAuthorize only production domains and use Firebase Security Rules to protect data.High
Content Security PolicyAllow only the Firebase and Google origins actually required by the chosen SDK and sign-in flow; review policy changes before rollout.Medium
Cost and operationsCheck current pricing, quotas, monitoring, recovery, and support requirements; “zero-overhead” does not guarantee zero cost.Medium

Combining WIF for keyless CI/CD, Secret Manager for runtime credentials, and Firebase Authentication for user identity can reduce static-key exposure and simplify operations. The result is only as strong as its IAM boundaries, provider conditions, data rules, and ongoing review.
